# Production release and migration runbook

This is the required operator procedure for staging and production. Local tests validate code and representative PostgreSQL histories; they cannot establish the state of a remote Supabase project, Vercel settings, Valmont-Pay tenant, DNS, or live payment rail.

## 1. Ownership and prerequisites

Assign one named release operator and one reviewer. Record the Git commit, UTC start time, environment, migration SHA-256, backup/PITR identifier, deployment URL, and all verification results in the release ticket. Never paste secret values into that ticket.

Required access:

- Supabase project/database administrator for staging and production;
- Vercel project administrator;
- Valmont-Pay tenant administrator;
- a test shopper account and a separate allowlisted admin account;
- an approved dealer test account and a normal/non-approved account.

Before any production change:

1. Confirm Supabase backups and point-in-time recovery are healthy. Take or identify a fresh restorable backup.
2. Confirm the gateway webhook signing secret and hosting value match without exposing either value.
3. Confirm `VALMONTPAY_SECRET_KEY`, `VALMONTPAY_WEBHOOK_SECRET`, and `SUPABASE_SERVICE_ROLE_KEY` exist in the target hosting environment. Configure the Upstash REST pair for a distributed production rate limit.
4. Confirm gateway callback allowlists include only the intended production host and its required `www` alias.
5. Confirm Supabase Authentication URL Configuration includes both exact production recovery URLs in [`AUTH_REDIRECTS.md`](AUTH_REDIRECTS.md). Do not begin rollout if either callback is absent.
6. Confirm no incident or migration is already in progress.
7. Schedule a short checkout maintenance window. The migration revokes insecure legacy RPC privileges, so an old client may be unable to check out after the migration. Security must fail closed during this interval.

## 2. Freeze and qualify the release

From a clean checkout of the exact release commit:

```bash
npm ci
npm audit --audit-level=high
npm run ci
git diff --check
git status --short
sha256sum supabase/migrations/20260814000100_production_hardening.sql
```

Pass criteria:

- dependency audit has no high/critical finding;
- every quality-gate command exits zero;
- the working tree contains no unexplained change;
- `public/` was generated by the gate and not hand-edited;
- the recorded migration checksum is from the same commit being deployed;
- CI is green for the exact commit.

Do not bypass the gate because a change appears documentation-only: CSP hashes, HTML, sitemap, cache behavior, and generated assets are intentionally coupled and fail closed.

## 3. Staging migration

Use a direct PostgreSQL connection intended for migrations, not the public anon key. Keep the connection string in a protected process environment or secret manager; do not commit it or place it directly in shell history.

```bash
psql "$STAGING_DATABASE_URL" \
  --set=ON_ERROR_STOP=1 \
  --single-transaction \
  --file=supabase/migrations/20260814000100_production_hardening.sql
```

The file is idempotent across the two supported historical schema shapes and contains fail-closed privilege assertions. Any error aborts the transaction. Save the redacted command result in the release record.

If the organization uses Supabase CLI migration history instead, link the repository first, verify the target project reference twice, run a dry-run/schema diff where supported, and then use the approved `supabase db push` workflow. Do not run `db reset` against a remote environment.

### Required post-migration SQL checks

Run these in the target SQL editor or through `psql`. Save results without customer/order data.

```sql
-- Payment mutations must not be available to browser roles.
SELECT p.proname,
       pg_get_function_identity_arguments(p.oid) AS arguments,
       has_function_privilege('anon', p.oid, 'EXECUTE') AS anon_exec,
       has_function_privilege('authenticated', p.oid, 'EXECUTE') AS auth_exec,
       has_function_privilege('service_role', p.oid, 'EXECUTE') AS service_exec
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND p.proname IN (
    'create_pending_order', 'confirm_order_paid',
    'set_order_payment_reference', 'set_order_customer_snapshot',
    'ensure_customer_for_checkout', 'release_order_reservation',
    'release_expired_order_reservations'
  )
ORDER BY p.proname, arguments;

-- Every security-relevant table must have RLS enabled.
SELECT relname, relrowsecurity
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND relname IN (
    'orders', 'customers', 'products', 'reviews', 'dealer_accounts',
    'drop_flips', 'delivery_fees', 'delivery_settings', 'sms_leads'
  )
ORDER BY relname;

-- Direct anonymous mutation must be absent.
SELECT table_name, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
  AND grantee = 'anon'
  AND privilege_type IN ('INSERT', 'UPDATE', 'DELETE')
  AND table_name IN ('orders', 'customers', 'sms_leads');

-- Shopper RPC grants must be authenticated-only (not PUBLIC/anon).
SELECT routine_name, grantee, privilege_type
FROM information_schema.routine_privileges
WHERE specific_schema = 'public'
  AND routine_name IN (
    'submit_product_review', 'claim_daily_drop', 'get_my_orders',
    'apply_for_dealer', 'get_my_dealer_profile', 'get_my_dealer_prices'
  )
ORDER BY routine_name, grantee;

-- Catalog projection is public; its source table and wholesale field are not.
SELECT
  has_function_privilege('anon', 'public.get_storefront_catalog()', 'EXECUTE') AS anon_catalog_exec,
  has_table_privilege('anon', 'public.products', 'SELECT') AS anon_products_select,
  jsonb_path_exists(public.get_storefront_catalog(), '$[*].wholesale_price') AS leaks_wholesale;
SELECT policyname, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public' AND tablename = 'products';
```

Expected results:

- every payment-mutation row has `anon_exec = false`, `auth_exec = false`, and `service_exec = true`;
- every listed table has `relrowsecurity = true`;
- the anonymous table-mutation query returns zero rows;
- shopper-private RPC execution is present for `authenticated` and absent for `anon`/`PUBLIC`;
- `get_storefront_catalog()` is executable by `anon` and returns no `wholesale_price`, while `anon` has no direct `SELECT` grant on `products`;
- the only `products` table policy is the allowlisted admin policy.

Investigate any extra overload. Do not approve based only on a matching function name.

### Platform tables (`20260829_platform_security.sql`)

The swap & sell marketplace, UK/US used board, wholesale portal and partner program
ship their tables in `20260828_platform_tables.sql` and the security model that
actually governs them in `20260829_platform_security.sql`. The follow-up must run
after both `20260811_admin_email_allowlist.sql` (it supplies `is_valmont_admin()`)
and the platform tables migration:

```bash
psql "$STAGING_DATABASE_URL" \
  --set=ON_ERROR_STOP=1 \
  --single-transaction \
  --file=supabase/migrations/20260829_platform_security.sql
```

The follow-up converges the earlier file (drops its TO-less policies, rebuilds any
platform table whose columns do not match) and **refuses to run if one of those
tables already holds rows**: it prints which table, how many rows, and which
columns are missing or must go. Empty the table after exporting it, then re-run.

Then set the identity pepper **once per project** (it salts the Ghana Card
fingerprint; without it the fingerprint is an unsalted SHA-256 of an
eleven-character ID, which is brute-forceable if the table is ever dumped):

```sql
ALTER DATABASE postgres SET valmont.identity_pepper = '<32+ characters from the secret manager>';
```

Rotation is not free: changing the pepper orphans every existing fingerprint, so
duplicate detection only resumes after each seller re-submits their card. Record
the pepper's fingerprint (not its value) in the release record.

```sql
-- No browser role may mutate a platform table; the only writes are RPCs.
SELECT table_name, privilege_type, grantee
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
  AND table_name IN ('sellers','swap_listings','swap_leads','used_inventory','wholesale_dealers',
                     'wholesale_orders','partner_applications','ad_payments','admin_audit_log','write_quota')
  AND grantee IN ('anon','authenticated')
  AND privilege_type <> 'SELECT';

-- The console's single entry point and the board must not be callable anonymously.
SELECT has_function_privilege('anon', 'public.admin(text,jsonb)'::regprocedure, 'EXECUTE') AS anon_admin,
       has_function_privilege('authenticated', 'public.admin_platform_board(text,integer)'::regprocedure, 'EXECUTE') AS auth_board;

-- Identity material must not be readable in the clear from any read model.
SELECT count(*) AS leaks_card
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
  AND pg_get_functiondef(p.oid) ILIKE '%ghana_card_hash%'
  AND p.proname LIKE 'get_%';

-- A promotion cannot be activated without the admin predicate.
SELECT prosrc LIKE '%is_valmont_admin()%' AS checks_allowlist
FROM pg_proc WHERE proname = 'admin_set_promotion';
```

Expected results:

- the grant query returns **zero rows**;
- `anon_admin = false` and `auth_board = true` (the function re-checks the
  allowlist, so `true` here only means "callable", not "authorised");
- `leaks_card = 0`;
- `checks_allowlist = true`.

Then sign in as the allowlisted admin and confirm `admin-control.html` renders
non-zero counters. A console that shows `—` everywhere means the board RPC was
revoked or the allowlist does not match the signed-in email; the page cannot fix
that, and it deliberately shows nothing rather than demo data.

`npm run test:migration` runs `scripts/test-platform-migration.mjs`, which
repeats these guarantees against a throwaway Postgres (PGlite), including
"client-supplied prices are ignored" and "a seller cannot publish their own
listing". Deploy the same commit only if that suite is green.

## 4. Staging application verification

Deploy the same commit to a protected staging URL with staging-only credentials, then run:

1. Check all seven pages return 200 and assets load without CSP console violations.
2. Confirm response headers match `vercel.json`: strict CSP, HSTS on HTTPS, frame denial, referrer/permissions policy, and MIME sniffing prevention.
3. Confirm HTML/service worker/manifest are revalidated and a fingerprinted build asset has one-year immutable caching.
4. Confirm `/api/valmontpay/webhook` rejects GET with 405 and an unsigned POST with 401; it must not return a stack trace.
5. Submit malformed and oversized checkout bodies and confirm clean 4xx responses.
6. Sign in as a normal account, reload, and confirm account data belongs only to that account. Log out and confirm private storage/UI is cleared.
7. Forge dealer values in local storage/Auth metadata and confirm dealer UI remains unavailable. Verify Pending and Suspended users receive no dealer-price response and retail checkout, Approved users receive matching protected RPC/checkout prices, public catalog responses contain no wholesale fields, and every order stores its actual `pricing_tier`.
8. Confirm account order history returns only the signed-in account's orders.
9. Create a Pending test order through checkout. Confirm authoritative price, delivery, reservation, account UUID, and idempotency behavior in the database.
10. Run a staging/test-channel payment and replay its webhook. Confirm one Paid transition and no second stock change.
11. Confirm bad amount and bad gateway-reference probes never mark an order Paid.
12. Request a customer password reset from both the storefront and account page. Confirm both emails return to `/account.html`, an expired link fails closed, a valid link updates the password, and the new password can sign in.
13. Confirm admin login, product management, and Daily Drop access with an allowlisted admin; deny the same calls to a normal account. Verify the neutral admin reset flow returns only the allowlisted admin to `/admin-login.html`, rejects customer recovery sessions, and updates the admin password with a valid link.
14. Check logs for raw tokens, keys, full webhook bodies, stack traces, or personal data. None should be present.

Do not use production service-role or gateway secrets in staging.

## 5. Production rollout

1. Enable the checkout maintenance notice or otherwise stop new checkout starts.
2. Reconfirm the production backup/PITR point and target project reference.
3. Apply the exact checked migration once using the production database URL and the staging command pattern.
4. Run all post-migration SQL checks immediately.
5. Deploy the exact green commit. Vercel must run the repository build and publish only `public/`; do not deploy the repository root manually.
6. Verify the canonical redirect and production response headers from an external network.
7. Run the non-payment staging checks against production with dedicated test accounts.
8. Execute the controlled [GH₵1 live-payment test](VALMONTPAY_LIVE_TEST.md), including webhook replay and cleanup/refund.
9. Re-enable checkout only after the live test passes.
10. Monitor for at least 30 minutes, then record release approval.

## 6. Monitoring and alerting

Alert on:

- checkout or webhook 5xx responses;
- elevated 429s or distributed-limiter failures;
- webhook 401 spikes (possible secret mismatch/attack);
- `amount_mismatch`, `gateway_reference_mismatch`, `manual_review`, or `insufficient_stock` logs;
- Pending orders/reservations older than the configured expiry;
- a surge in gateway initialization failures or reservation releases;
- Supabase Auth/RPC latency and failures;
- CSP violation reports if a reporting endpoint is introduced;
- unexpected changes to DNS, Vercel environment variables, gateway callbacks, or Supabase roles/policies.

Logs should identify order/reference outcomes but must not include bearer tokens, service keys, webhook secrets/signatures, full addresses, or payment payloads. Restrict log access and retention.

## 7. Rollback and incident response

### Application/configuration failure

- Disable checkout first if payment/order state is uncertain.
- Roll back only to a previously verified build that is compatible with the hardened database contract.
- Do **not** redeploy a legacy browser-authoritative checkout: the migration intentionally revoked its privileges.
- Purge/revalidate HTML at the CDN when configuration changes. Fingerprinted assets are safe to retain. A newly generated service worker uses a content-derived cache name and removes obsolete caches on activation.
- Re-run endpoint, Auth, storage, CSP, and one controlled checkout verification before reopening.

### Database migration failure

- A failure inside `--single-transaction` should roll back automatically. Confirm this; do not assume it.
- Never “fix” the incident by granting payment RPC execution back to `anon` or `authenticated`, disabling RLS, or restoring anonymous table writes.
- Prefer a reviewed forward-fix migration. If data corruption makes recovery necessary, stop checkout, preserve logs, use the pre-release PITR/backup under the database incident procedure, and reconcile any gateway payments created after the restore point before reopening.
- There is intentionally no generic down migration: reversing these grants/RLS changes would recreate a known payment and authorization vulnerability.

### Secret exposure

1. Disable affected checkout/webhook paths if exploitation is possible.
2. Rotate at the source provider first, then update the hosting secret and redeploy.
3. For a webhook secret, update both gateway tenant and receiver in a coordinated maintenance window.
4. Revoke the old Supabase service-role JWT by rotating project signing credentials only through the provider's documented process; assess all consumers first.
5. Review access/payment/audit logs from the earliest possible exposure, reconcile orders and inventory, and document customer/regulatory notification decisions.
6. Remove leaked material from Git history/artifacts/logs where applicable. Rotation is mandatory even after removal.

## 8. Release completion record

The release is complete only when the ticket contains:

- exact Git commit and green CI link;
- migration filename and SHA-256;
- staging and production backup/PITR references;
- staging and production migration/post-check outcomes;
- production deployment identifier;
- external header/cache/CSP checks;
- GH₵1 reference, Paid/idempotency/stock results, and refund/cleanup status;
- monitoring window outcome;
- operator and reviewer approval.
